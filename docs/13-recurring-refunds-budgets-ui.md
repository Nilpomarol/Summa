# Recurring, Refunds and Budgets UI - Android P4

> Scope: P4-1. This refines the Android screens needed for Phase 4: recurring templates, the recurring list and due prompts, refunds, budgets, and notification/alert settings. It does not add product rules beyond `docs/00-Full_Spec.md`, `docs/04-data-model.md`, `docs/08-design-system.md`, or `docs/09-app-architecture.md`. It is documentation and string preparation only — no repository or production screen is implemented in P4-1.

---

## 1. Phase Scope

P4 adds the time-based and limit-based layer on top of the ledger:

- create and manage recurring **templates** for expense, income, and transfer;
- generate **due prompts** (virtual occurrences) from active templates and confirm/skip them;
- show a **recurring list** ordered by day with a monthly total;
- create **refunds** linked to an expense, with the optional shared-expense actual adjustment;
- create and track **budgets** (category-monthly first), evaluated limit vs. actual;
- schedule **local notifications**: recurring lead-time reminders, budget-threshold alerts, low-balance alerts;
- surface a **recurring-cost summary** built from active templates.

P4 must not implement trips/tags attachment in the template UI beyond the optional model field (Phase 5 owns trips), the desktop **recurring calendar** (Phase 6B owns it), CSV import, sync, or forecasting. Budgets ship **category-monthly first**; overall-month and trip scopes are fast-follows tracked in the roadmap, not built in P4 unless the roadmap is updated. Auto-categorization rule management UI is not part of P4 (the matching rule already exists; rule CRUD is a later concern).

## 2. Navigation Shape

Phase 4 adds **Recurrents** under the Gestió hub, per `docs/07-ui-ux.md` §IA. The primary Android destinations remain:

- Inici;
- Moviments;
- centered New movement FAB;
- Anàlisi;
- Gestió.

Budgets are reached from Analysis/Categories management and from a category's detail, not from the bottom bar; a category-scoped budget is created or edited from the category context so the scope is preserved. Refunds are not a destination: a refund starts from an **expense's** movement detail (`Add refund`). Notification and alert settings live under **Gestió > Configuració** (system tools, §5.8). Recurring templates live under **Gestió > Recurrents**. The global "New movement" action is unchanged and remains centered in the bottom bar; "New recurring" starts from Recurrents, and "New budget" from the budgets surface.

## 3. Recurring List (mobile)

Purpose: show what repeats, when the next occurrence is due, and the month's recurring load.

Content:

- title: Recurring;
- monthly summary strip: total of this month's recurring expenses, income, and net (signed, semantic colors), built from active templates due in the visible month;
- **due section** at the top when one or more occurrences are pending: each due prompt as a row (see §4), plus confirm-all / skip-all when several are queued;
- **scheduled section**: active templates ordered by next due day-of-month, each row showing icon/category, name, account, signed amount (or "variable" marker when `amount_is_variable`), cadence label (e.g. "Mensual · dia 1"), and next due date;
- paused templates grouped/dimmed below or behind a filter; ended/archived templates hidden by default;
- empty state with a New recurring action and a one-line explanation.

Actions:

- New recurring (opens Add template, §5);
- open template detail/edit;
- per-item: Add payment (confirm), Skip this period, End recurring, Edit template;
- confirm-all / skip-all for the queued due prompts.

Data rules:

- the visible monthly total is **derived** from active templates and their schedule; it is informational and never a ledger value;
- pending occurrences are **virtual** — not movements — and do not affect balances, flow, or analysis until confirmed (§3.10, §4.3);
- amounts use Geist Mono/tabular figures, euros only at the UI edge.

Visual identity:

- reuse the design-system list-card row (icon chip, title, subtitle, right-aligned `MoneyText`);
- variable-amount templates show a neutral "variable" pill instead of a fixed amount;
- cadence and next-due use muted label text.

## 4. Recurring Due Prompts

Purpose: let the user materialize or dismiss each occurrence that has come due, one per missed period.

Content:

- one prompt row per due occurrence, generated by the advancement rule (`recurring_advance` golden) from the template's `next_due_date` up to today;
- each prompt shows the pre-filled concept, due date, account, and amount (editable on confirm); variable-amount prompts show the estimated/blank amount for the user to fill;
- a distinct "due" visual treatment (e.g. alert/accent banner or a highlighted card) separating prompts from scheduled templates;
- when several are queued, a confirm-all and a skip-all control.

Behavior:

- **Add payment / Confirm** — opens the pre-filled movement form (the existing Add/Edit movement flow, carrying the previous split forward for shared templates), editable before save; on save it creates the movement with `template_id` set and advances the template cursor;
- **Skip this period** — dismisses this occurrence and advances the cursor, no movement created;
- editing a confirmed instance while the recurring flag stays set updates the template (§4.3);
- confirm-all materializes each queued occurrence with its pre-filled values; skip-all advances past all of them; both are dismissible/undoable, never silent;
- nothing is auto-added without confirmation.

Data rules:

- the prompt set comes from the advancement rule and must match the `recurring_advance` golden vector;
- month-end clamping applies (day-31 → last day of shorter months);
- prompts never write to the ledger until confirmed.

## 5. Add/Edit Template

Purpose: maintain the template that drives recurrence; it mirrors the movement form plus a schedule.

Fields:

- **movement pre-fill:** type (expense / income / transfer), amount (or "variable"), account (+ destination for transfer), category (expense/income only), name, payee, notes, shared split config (expense only, reusing the Split editor);
- **schedule:** frequency (weekly / fortnightly / monthly / yearly / custom), anchor (day-of-month for monthly/yearly, weekday for weekly/fortnightly), custom interval (`interval_count` + `custom_unit` days/weeks/months/years), next due date;
- **flexibility:** amount flexibility (± margin, optional) and "variable amount" toggle; date flexibility (± days, optional);
- **notification:** lead notification days (optional; falls back to the global default);
- **status:** active / paused (end is a separate per-item action).

Validation:

- hard errors only for schema-invalid data: non-positive fixed amount (unless variable), missing account, transfer without a distinct destination, category set on a transfer, custom frequency without interval+unit, non-custom frequency carrying interval/unit, anchor out of range;
- a shared template requires a reconciled split, same as a one-off shared expense;
- warnings (never blocking) for unusual but valid setups.

State:

- form state belongs in a ViewModel; save returns validation errors for schema-invalid input only;
- toggling "variable amount" clears/relaxes the fixed-amount requirement and prompts for the amount at confirm time.

## 6. Refund Flow

Purpose: record money returned for a specific past expense without it counting as income.

Entry point:

- expense **movement detail** → Add refund (refunds are only creatable against an expense).

Fields:

- linked expense (fixed from the entry point, shown for context with its amount and remaining un-refunded amount);
- amount (the cash inflow to the account);
- account (where the money landed; defaults to the original expense's account);
- optional **actual-refund amount** — shown only when the original expense is shared, representing the portion attributable to the user's own share when it differs from the cash inflow;
- category (inherited from the original by default; editable);
- date; optional notes/payee.

Behavior:

- saving creates a `movement` with `type='refund'`, `refunds_expense_id`, account, amount, date, category, and optional `actual_refund_cents`;
- a refund is an **inflow** on its date (account balance up) but **never** income; in analysis it nets down the carried category in the refund's own period (§3.3b, `refund_actual` golden);
- if the refund amount exceeds the original's remaining un-refunded amount, show an inline over-refund warning and allow override;
- if the original expense is archived, its linked refunds are surfaced for the user to reassign or remove, never silently orphaned.

Data rules:

- the actual adjustment defaults to the cash amount; for a shared expense it is only the user's share, carried explicitly in `actual_refund_cents`;
- all amounts parse to integer cents before save; euros only at the UI edge.

## 7. Budgets

Purpose: a planned limit compared against actual spend, informational only.

Scope for P4: **category-monthly** (`scope='category'`, `period='monthly'`). Overall-month and trip budgets are fast-follows and out of P4 unless the roadmap is updated.

Budgets list:

- reached from category management / analysis;
- each budget row shows category, monthly limit, this-period actual, remaining/over, and a progress bar colored green / amber / red by threshold;
- empty state with a New budget action.

Add/Edit budget:

- fields: category (expense-supporting), monthly limit amount, optional alert threshold percent (1–100), start date (optional);
- validation: positive limit, a category required for category scope, threshold within 1–100;
- save returns schema-invalid errors only.

Evaluation:

- limit vs. the sum of relevant **actual** expenses for the month (§4.5, derived via the canonical actual views);
- progress bar thresholds: under threshold = green, at/over threshold = amber, over limit = red;
- budgets **never block** input; they inform.

Budget surfacing elsewhere:

- a budgeted category shows its budget bar in the category breakdown / category detail (reusing the same progress component);
- the bar is derived and read-only there.

## 8. Notifications & Alerts

Purpose: offline, local reminders and alerts; configured under Settings.

Settings content (§5.8):

- **Recurring reminders:** global default lead time (days before due); per-template `lead_notification_days` overrides it;
- **Budget alerts:** toggle; fire when a budget reaches its threshold or goes over;
- **Low-balance alerts:** toggle; fire when an account falls below its optional `low_balance_threshold_cents` (§3.1).

Behavior:

- all notifications are scheduled locally (no network); the app is local-first;
- a reminder for a recurring item points the user at the due prompt; it does not auto-confirm;
- alerts are informational and never block input or mutate data;
- scheduling respects archived/paused state: paused templates and archived accounts/budgets produce no alerts.

P4 scope note: the settings UI and the local-scheduling wiring land in P4-7; P4-1 only defines the screen content and strings.

## 9. Movement List and Detail Integration

Movement list:

- recurring-materialized movements may show a subtle recurring marker (an instance has `template_id`); this is orthogonal to the shared/paid-by markers;
- refunds appear as inflow rows with the refund type color and the carried category;
- settlements and shared markers from P3 are unchanged.

Movement detail:

- an **expense** shows its linked refunds (a refund list with each refund's date/amount) and the Add refund action;
- a **refund** shows its linked original expense, the cash amount, the actual-refund adjustment when present, and the carried category;
- a recurring instance shows it is part of a series with an affordance to open the template; unmarking recurring detaches the instance from the template (template untouched);
- all delete actions remain soft-delete.

Drill-down:

- recurring prompts are not ledger rows and are reached only from the Recurring screen;
- refund and budget aggregates that resolve to real movements open the movement list.

## 13. Recurring Pattern Detection (mobile) — added P5R-13

**Purpose:** a user-triggered scan (spec §3.10 addendum) that mines movement history for likely recurring expense/income patterns — both still-ongoing ones and ones that already stopped — and proposes new or updated `templates` for the user to review and confirm. Never automatic; never applies anything without per-item confirmation.

**Trigger:** a `TopBarIconButton` (sparkle/"auto-awesome" icon) trailing the Recurring list's `SectionHeader`, disabled while a scan is running. Tapping it runs the scan on the IO dispatcher against the full active movement + template list, with no other UI change until it completes.

**Review sheet:** a `ModalBottomSheet` listing every detected candidate as a `FinanceCard` row: name, a `NeutralPill` badge ("Nou" for a new template / "Actualitza" for a match against an existing template of any status), cadence + suggested status + occurrence count, and the derived amount (fixed, or a "Variable" pill). Each row has a checkbox, pre-checked; unchecking skips that candidate. Bottom actions: Cancel, and "Confirma els seleccionats" (only shown when there's at least one candidate). An empty-state message shows when nothing was detected.

**Data rules (mirrors the spec §3.10 addendum verbatim):**
- Scoped to weekly/fortnightly/monthly cadence and expense/income movement types only.
- Groups movements not yet linked to a template by account + category + normalized name/payee; requires ≥3 occurrences with a consistent gap (tolerates one missed occurrence — see the known limitation below for the boundary of that tolerance).
- Matches against existing templates of any status (active/paused/ended) for update-vs-create; movements already linked to a template are excluded from grouping.
- A stale detected pattern (last occurrence well past its own cadence) defaults to a proposed `ended` status; a recent one defaults to `active`. Both remain reviewable before confirming — nothing is auto-applied.
- Deleting a template severs its movements' links (they stop showing the recurring badge and become eligible for re-detection); ending a template does not. Deleting a movement can optionally roll its template's due date back, but only when that movement is provably the template's immediate prior occurrence (see rows 10-14 below).

**Known limitation (not yet fixed):** cadence classification (`RecurringPatternDetector.classifyCadence`) compares *consecutive* gaps against a fixed day-range band (e.g. 27-31 days for monthly) rather than each occurrence's distance from an inferred anchor day. A subscription whose billing date drifts by even 1-2 days (weekends, bank processing) can push two or more gaps outside the band at once, and the whole group gets silently dropped rather than degraded — this is most likely to bite a genuinely new pattern that was never linked to a template before (an existing template's own history isn't affected, since it's matched by signature, not re-derived). Diagnosed but deliberately deferred (2026-07-05) since the delete/unlink defect below was judged the more likely cause of reported "detection isn't working" symptoms. If revisited, the fix is to switch to anchor-based deviation: infer the expected day-of-month/weekday first, then check each occurrence's distance from that anchor instead of from its neighbor.

**Implementation notes (fixes applied after initial ship, full history in `docs/06-roadmap.md` P5R-13):**
- Editing a template's Status field (including a detected "Actualitza" candidate's suggested status) silently had no effect — `Templates.sq`'s `updateTemplate` omitted `status` from its SET clause. Fixed.
- A detected match against an existing template of a *different* movement type could be misidentified as the same pattern. Fixed by including `type` in the signature match.
- Confirming a template never linked its source movements to it, so the same movements kept re-surfacing as "Actualitza" on every future scan. Fixed via `MovementRepository.linkToTemplate()`.
- A failure partway through confirming several accepted candidates could abandon the rest and, on retry, duplicate an already-created template. Fixed by applying each candidate independently and only retrying genuinely failed ones.
- Deleting a template never unlinked its movements (the mirror image of the fix above) — they stayed excluded from detection forever. Fixed via `MovementRepository.unlinkAllForTemplate()`, atomic with the archive.
- Deleting a movement never offered to un-advance its template's due date, even when that movement was provably the last real occurrence. Fixed via `RecurringAdvancer.isImmediatePriorOccurrence()`, scoped to ACTIVE templates only and gated behind an opt-in checkbox.

**Manual checklist:**

| # | Step | Expected |
|---|------|----------|
| 1 | Seed several months of a same-account/category/name expense ~30 days apart, without marking any as recurring, then tap the detect icon on the Recurring list | Review sheet opens with a "Nou" candidate showing plausible monthly cadence, day, and amount |
| 2 | With two or more candidates listed, uncheck one, then confirm | Only the checked candidate(s) appear as new templates afterward; the unchecked one does not |

| 13 | Same setup, but leave the checkbox unchecked when confirming | The due date stays advanced — today's behavior, unchanged |
| 14 | Confirm two consecutive occurrences, then delete the *older* one | The archive-confirmation dialog shows no checkbox at all — only the immediately preceding occurrence ever offers to revert the due date |

## 14. Due Reminders Sheet (mobile) — auto-surfaced app-open prompt

**Purpose:** due recurring items (`RecurringUiState.duePrompts`) previously only showed as a passive list inside Management > Recurring — the user had to remember to go look. This surfaces them proactively as a `ModalBottomSheet` shown automatically once per app cold start, without requiring any navigation.

**Trigger:** `MainActivity` calls `recurringViewModel.onScreenShown()` on first composition (so due-prompt data is ready before any navigation happens) and renders `DueRemindersSheet` whenever `duePrompts` is non-empty, no other recurring dialog is open (`RecurringUiState.hasOpenDialog`), no unrelated movement dialog is open either (`MovementsUiState.hasOpenDialog` — avoids stacking on top of, e.g., the FAB's "add movement" form if it happens to be open at the same moment), and the sheet hasn't already been shown this app process — a plain `remember` flag, not persisted, since a genuine process restart is exactly what "once per cold start" means.

**Content:** the same `DuePromptCard` already used in the in-screen passive list, one per due item, each offering: **Afegeix pagament** (confirm — opens the existing confirm form), **Omet aquest període** / **Omet-los tots** (skip one / skip all pending for that template), and **Finalitza la sèrie** (opens the existing end-confirmation dialog — new: previously ending a template was only reachable from its own ⋮ menu, disconnected from the due-prompt). A **Tanca** button dismisses the sheet without deciding.

**Persistence model:** dismissing without acting on every item does **not** clear anything — `duePrompts` is always recomputed live from each template's real `next_due_date`, so anything left unaddressed simply shows up again next cold start. Confirming or skipping an item shrinks the list normally; once every item is handled the sheet has nothing left to show. Opening a sub-dialog (confirm form, end confirmation) from within the sheet makes it step aside temporarily and reappear once that sub-dialog closes, as long as items remain.

**Architecture note:** `RecurringViewModel`'s dialogs (`ConfirmPromptDialog`, `TemplateFormDialog`, `DetectionReviewSheet`, the end/delete confirmations) were hoisted out of `RecurringScreen`'s own composable into a shared `RecurringOverlays(viewModel)` composable, since `recurringViewModel` is an app-level singleton (`MainActivity.kt`) and these dialogs must now render regardless of which screen is currently showing, not only when the user is on the Recurring screen itself. `RecurringOverlays` is rendered once, unconditionally, from `MainActivity` (mirroring the existing `MovementDialogHost` precedent for movement-related dialogs) — `RecurringScreen` no longer renders it itself.

**Manual checklist:**

| # | Step | Expected |
|---|------|----------|
| 1 | Seed a template whose `next_due_date` is today or earlier, force-stop and relaunch the app | The reminder sheet appears automatically on app open, without navigating anywhere |
| 2 | Tap "Afegeix pagament" on one item | The existing confirm form opens; the reminder sheet steps aside. Save it | The confirmed item disappears; the sheet remains open if other items are still due, or closes on its own if that was the only one |
| 3 | Tap "Finalitza la sèrie" on an item | The existing end-confirmation dialog appears; confirming removes that item from the sheet and from the Recurring screen's list |

| 6 | Navigate to Management > Recurring at any point | The passive in-screen due-prompts list still works exactly as before, independent of the auto-sheet, and now also shows a "Finalitza la sèrie" action on each card |
